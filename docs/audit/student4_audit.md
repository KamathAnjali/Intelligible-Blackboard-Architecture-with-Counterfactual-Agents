## 3. Fakes, placeholders, and integration hazards

- **Gold-bearing “live” feed:** `bench/ingest/krama_parser.py:237-248,277-299,301-346` labels itself synthetic, creates agents with `model_name="synthetic-fixture"`, and seeds `expected_answer` or reference steps into board entries. It is a visualization fixture, not task ingestion through agents/scheduler. Keep it out of performance evidence.
- **Synthetic trial results:** `bench/metrics/trial_runner.py:53-58` raises `NotImplementedError` for `pilot` and `full_study`; `:78-102` uses fixed outcomes, token values, and `0.001` timing in the example; `:437-483` makes synthetic task rows. The four pilot CSVs have 25 such simulated rows/config; each dry-run CSV has one row. `docs/week2_status_note.md:18-20` and `docs/final_rehearsal_notes.md:3,35-36` correctly withdraw old simulator claims.
- **Replay/mock fallback:** `ui/server/board_tap.py:52-62,153-203` defaults to LOG_REPLAY, uses a relative fixture path, then falls back to a canned synthetic stream when no valid snapshot exists. The UI has mode labels (`Canvas.tsx:60-70`), but default replay content is explicitly a synthetic fixture in `README.md:84`.
- **Token estimates:** `token_counter.py:80-117` falls back to about 1.3 tokens/whitespace word. `board_tap.py:82-109` counts prediction/explanation only and labels the result `estimated_board_entry_text_only`; `TokenTally.tsx:47-72` discloses that prompts are excluded. These are not provider-cost totals.
- **Counterfactual UI gap:** current worktree code can create a sandbox and record a simulated entry (`agents/conversation.py:218-300`; `blackboard/core.py:225-263`), but `board_tap.py:126-140` subscribes only to main-board `ENTRY_POSTED`. `record_counterfactual_result` persists state without emitting an event. Thus split-panel controls do not by themselves prove real rollback streaming.
- **Misleading stale TODO:** `ui/server/main.py:171-173` still says the scheduler should later emit directly and that `board_tap._run_live_tap()` should consume it; current bridge instead subscribes to the board emitter. Review/remove this stale note.
- **Chunk script:** pre-existing untracked `bench/run_benchmark_chunk.py:14-18,66-68,114-126` hardcodes 10 chunks × 11 rows, one Qwen model, localhost URL, evaluator path convention, and counterfactual fraction 0. It can only run allowlisted entries (`:74-95`); its “succeeded” count means subprocess exit code zero (`:128-141`), not a correct evaluator score. It is not a four-condition trial runner.
- **Fixed local endpoints/paths:** `ui/frontend/src/App.tsx:63-64` hardcodes `ws://localhost:8000/ws`; `board_tap.py:59-62` resolves the replay file relative to current working directory; `README.md:25-35,66-81` has Windows/WSL-specific PowerShell and a default Windows Ollama executable path. `ui/server/main.py:78-80` allows all CORS origins. These choices need configuration/documentation for non-local deployment or another machine.
- **Hardcoded content:** `bench/run_benchmark_chunk.py` does not hardcode task IDs, but its division and runtime configuration are fixed. The parser’s documented sample file `bench/data/sample.jsonl` does not exist. The source scan found no literal API credential; this does not audit credentials outside tracked source or local environments.
- **Unused/incomplete research modules:** `bench/metrics/trial_runner.py` is separate from `bench.kramabench_runner`; the real runner does not import it. `plotting.py` expects official-provenance trial CSV fields, while the current task runner archives per-task evaluator outputs rather than writing those paired ablation rows. The modules run as standalone CLIs, but the real benchmark pipeline does not connect them.

## 4. Run results and frontend/backend contract

### Contract

Backend emits `connection_ack`, `board_entry`, `session_started`, `session_summary`, `session_error`, and `stream_complete` (`ui/server/main.py:119-151,175-190`). `board_entry` also embeds `token_tally` (`board_tap.py:95-109`). The frontend consumes `connection_ack`, `board_entry`, nested `token_tally`, and `stream_complete` (`App.tsx:102-139`); it declares `session_summary` but does not render it, and does not handle `session_started` or `session_error`. There are no active-agent or scheduler-turn events. `session_error` currently reaches backend logs but not a visible error panel.

The explicit `/ws/mock` endpoint sends canned mock entries (`main.py:200-219`). The primary `/ws` endpoint identifies mode in its handshake (`:175-190`). The bridge test verifies a real scheduler submission, while no browser test verifies graph rendering or a full live task.

### Archived task evidence

Under `archive/full-c1-*` through `archive/full-c6-*`, all eight task outputs contain manifests, task records, and evaluator-measure CSV files. Seven failed before a score: evidence-size limit, repeated-invalid-request stops, PXP turn limits, or the 12-tool cap. `archive/full-c6-legal-legal-easy-9/` is the only manifest with `status=success`; its measure CSV records `success=0.0`. All eight manifests record `counterfactual_fraction=0.0`, `counterfactual_simulations=0`. The `p223-smoke-r1` record failed at PXP turn limit; it is not a passing smoke result. Therefore, current run evidence confirms a functioning per-task execution path, but not successful accuracy or counterfactual benefit.
